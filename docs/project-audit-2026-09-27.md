# Layerive 项目审查与产品提升建议

审查日期：2026-09-27。对象：当前工作区代码，包含审查开始前已存在的未提交修改。

## 结论

Layerive 已经具备有用的产品基础：本地项目管理、图片版本树、可配置模型、中文改字、参考图局部替换，以及逐张返回的变量批量生成。最有价值的组合是“围绕已有图片持续修改，并保留过程”，而非单独的文生图入口。

当前主要问题是三个方面：

1. **可靠性尚未与功能数量匹配。** 保存冲突、重复提交、版本来源断开等问题会损害用户对创作工具的信任。
2. **从生成到交付还缺少关键步骤。** 缺少失败项重试、品牌约束、结果验收、指定规格导出和可复用的任务配方。
3. **面向谁解决什么问题还不够集中。** 可以优先验证“中文电商与营销素材的批量改版工作台”，再决定是否扩大范围。

建议顺序：修复数据与任务问题 → 完成批量交付流程 → 用真实场景验证差异化 → 再扩展模型与协作能力。

## 一、已复现的缺陷

### B01 · P1：项目 PATCH 会把并发保存的内容覆盖回旧值

位置：`server/index.mjs:2627–2630`。

处理逻辑先 `projectOrThrow()` 读取整行，再 `await body(req)`，最后用旧整行补齐所有未提交字段并更新。读取请求体期间其他请求可以更新项目。

复现：保持重命名请求的请求体未发送完；先完成另一个草稿保存请求；最后发送完重命名请求。结果项目名称更新成功，但刚保存的 `draft.prompt` 消失，草稿变回 `{}`。

影响：重命名、收藏、自动保存和多标签页操作之间会互相覆盖；表面上两个请求都成功。

修复：完整读取并校验请求体后再读状态；PATCH 只更新显式提供的字段。草稿另加 revision/乐观并发检查，区分“字段未提供”和“显式清空”。

验收：受控延迟下，重命名不能改变新草稿；收藏不能回滚当前图片；两标签页冲突有明确处理策略。

### B02 · P1：旧的自动保存响应会删除较新的本地恢复副本

位置：`src/WorkspaceView.tsx:547–556`。

`flushDraft()` 提交快照后，成功返回便无条件 `localStorage.removeItem(draftCacheKey)`，没有检查用户是否已继续输入。

复现：旧快照 A 的保存请求等待响应时，写入新快照 B 的本地副本；随后 A 返回成功。B 的恢复副本被删除。

影响：较新内容尚未保存时会短暂显示“已保存”，异常退出或页面被丢弃时可能失去恢复副本。正常 pagehide 可能重新写入，但不能作为崩溃或所有页面回收场景的保证。

修复：每次编辑分配 revision；保存队列串行或合并；仅当响应对应当前 revision 时清理恢复副本并显示“已保存”。本地存储异常不能被误报成服务端保存失败。

验收：A 请求晚回时 B 始终保留；自动保存与离开工作台触发的保存不会互相覆盖。

### B03 · P1：生成请求返回前可重复提交，产生多个任务

位置：`src/WorkspaceView.tsx:1237–1246`；后端 `server/index.mjs:1226`。

`send()` 仅检查 `generating`，但它在 `api.generate()` 返回、调用 `startPolling()` 后才变为 true。请求未返回时，按钮和快捷键仍能再次提交；后端没有请求幂等键。

复现：执行实际 send 回调，延迟第一次请求响应，连续调用两次，记录到两次 generate 请求。

影响：额外模型调用、潜在额外费用；前端单任务轮询还可能只跟踪最后返回的任务。

修复：调用前同步设置提交锁，失败后释放；添加客户端 requestId 和服务端幂等记录。网络超时后先查询提交结果，避免直接重复创建。

验收：双击、重复快捷键、响应丢失重试只产生一个逻辑任务；明确新建任务仍可正常执行。

### B04 · P1：生成途中删除输入版本，完成结果会挂到已删除父节点

位置：`server/index.mjs:2034–2056`、`server/index.mjs:1357`。

删除仅检查被删版本自身是否正在生成，以及已经存在的子版本。普通生成任务的输出版本在完成时才创建，因此此时还查不到子版本。

复现：从 V1 开始生成下一版；任务未完成时删除 V1，接口成功；任务完成后的新版本仍引用被删除的 V1。Bundle 中输入图片也被隐藏，返回 `inputs: []`。

影响：版本树失去可见来源、对比与溯源失败；文件本身仍在，但用户难以理解这次修改来自哪里。

修复：删除前检查在途任务输入及父版本引用，给出 409；或制定完整的重新挂接规则并在任务发布事务中再次验证父节点。对软删除输入保留必要的只读来源信息。

验收：普通生成与所有批量任务运行时，来源版本删除行为一致；完成结果不引用不可解释的父节点。

### B05 · P2：删除当前查看的历史版本后，当前图片可能悬空

位置：`src/WorkspaceView.tsx:491`、`server/index.mjs:2630`、`server/index.mjs:2050–2053`。

前端保存 `currentImageId`，没有一起保存匹配的 `currentVersionId`；删除逻辑主要根据 `current_version_id` 和封面判断是否回退图片。

复现：生成 V1、V2；通过 PATCH 将当前图片切回 V1，版本指针仍是 V2；删除 V1。返回项目的 currentImageId 仍指向已从 Bundle 隐藏的图片。

影响：画布空白、旧输入 ID 残留，后续操作容易报“图片不存在”。

修复：由服务端依据图片推导并原子更新版本指针；删除时独立检查当前图片、封面、草稿输入引用；前端同步清理或回退 inputImageId。

验收：删除非最新但正在查看/使用的版本后，画布、输入、项目指针全部指向有效图片或全部清空。

### B06 · P2：模型返回非图片内容也会被发布为生成成功

位置：`server/index.mjs:1351`，批量路径另见 `1608`、`1769`、`1945`。

当前无法读取图片尺寸时，回退到请求尺寸，继续写库和发布成功版本。

复现：本地模型返回合法 JSON，其中 b64_json 解码后是普通字符串。任务仍 success，输出声明为 image/png，打开文件得到原字符串。

影响：网关异常、损坏下载、MIME 不匹配时出现“生成成功但图片打不开”；进一步影响备份和下一次编辑。

修复：发布前统一校验实际图片解码、格式、像素与字节限制，从内容推导 MIME 和尺寸；错误输出不发布，保存明确诊断。下载模型 URL 的内容同样受限。

验收：HTML、JSON、截断图片、错误 MIME、超大像素结果均不能成功发布；合法 PNG/JPEG/WebP 正常通过。

### B07 · P2：ZIP 读取器不校验 CRC，无法可靠发现内容损坏

位置：`server/zip.mjs:73–110`。

写入器计算 CRC；读取器解压后没有验证 CRC 或声明的未压缩长度，同名条目也被 Map 静默覆盖。

复现：替换某 ZIP 条目的压缩内容，保持原始 CRC 不变；readZip 正常返回被修改的内容。

影响：有效 deflate 流内的数据损坏可能静默通过。恢复时的 SQLite integrity_check 不能替代图片和配置文件的完整性校验。

修复：校验 CRC、长度、目录边界、本地文件头和重复条目；如增加备份 manifest，可记录每个文件的 SHA-256。CRC 用于损坏检测，不能作为防恶意篡改的认证机制。

验收：修改内容但未更新校验值、重复路径、截断结构均被拒绝；历史合法备份继续可读。

## 三、工程优化：优先降低故障和维护成本

### 1. 拆分职责，但保留当前适合本地应用的技术栈

后端入口约 2,800 行，工作台约 1,731 行。当前业务仍适合 Node HTTP + SQLite + React，无需为拆分引入微服务。

建议后端逐步拆为：项目/版本服务、任务执行器、模型适配器、图片 I/O、备份导入导出、HTTP 校验。前三种批量执行器保留各自输入与阶段，复用逐项状态更新、取消、失败续跑和结果发布逻辑。

前端提取 `useProjectDraft`、`useGenerationTask`、`useBatchDraft`、Canvas、BatchPanel、TextEditor。先为保存和任务建立明确状态机，避免大量 boolean 形成不可能组合。

拆分必须保持 API 和数据兼容，每次只处理一条稳定边界，不能一次重写全项目。

### 2. 补齐两端共享的运行时契约

当前 TS 类型只检查前端，`tsconfig.json` 不覆盖 server `.mjs`；`npm run lint` 实际是 tsc，不包含 hooks 依赖或服务端静态检查。前端的 `Record<string, unknown>` 草稿和生成请求，也弱化了字段约束。

建议为项目 PATCH、生成参数、批量输入、模型配置、导入 manifest 定义可运行校验；明确 API/schema 版本。数据库添加迁移版本和旧数据迁移测试，避免后续每个功能都散落兼容分支。补 hooks lint，检查服务端类型可先采用 JSDoc/checkJs 渐进推进。

### 3. 优化图片与大项目读取

- 现有缩略图仅对 PNG 生效，且用 JS 同步解码/缩放；JPEG/WebP 回退原图。已有 Sharp 依赖，可统一生成三种格式缩略图，并限制并发、像素和缓存数量。
- 首页封面直接取原图（`HomeView.tsx:166,191`）；使用缓存缩略图与适当尺寸，列表也加入延迟加载。
- Bundle 每次返回全部消息、版本与图片；每个版本再查 inputs 并过滤图片，存在 N+1 查询及重复遍历。先一次聚合 inputs、按 versionId 分组，再考虑消息分页和版本增量同步。
- 草稿 PATCH 返回完整 Bundle，自动保存无需承受全历史序列化成本。可提供轻量响应，保留现有接口兼容期。
- 优先改成无重叠轮询和增量获取；有性能证据后再引入 SSE，不必把换传输技术当作首要目标。
- 备份当前同步 deflate、全量读入内存；大文件会占用事件循环与多份内存。采用流式归档/解包或独立工作进程。
- 画廊、模型配置、工作台可延迟加载，拆分 525 kB 主包；桌面端首屏收益需实测，不应夸大。

建议压测基线：1,000 张图片、500 个版本、长消息记录、50 项批量任务；记录打开项目耗时、自动保存耗时、内存峰值、UI 卡顿和取消响应。以上规模是建议测试条件，不是已测结果。

### 4. 将可靠性测试前移

新增正式回归测试应覆盖本文 B01–B07，以及批量草稿恢复、桌面 origin、候选分支对比、终态轮询失败。

引入少量关键浏览器测试：首次配置模型 → 创建项目 → 上传 → 生成 → 选第二张候选 → 局部修改 → 返回/刷新 → 导出。测试用本地模型 stub。CI 除 tag 发布外，在 pull request / 常规变更时运行构建与回归；桌面包增加隔离用户目录下的启动、Sharp 加载、退出检查。

### 5. 本地产品的维护体验

- `.bat` 写死开发机路径，应改为脚本自身目录；提供 Node 检查、端口冲突诊断。
- Electron 正式包 `stdio: ignore`，现场排障缺少后端日志；加入轮转日志与脱敏诊断包，避免把 API Key 或图片字节写进去。
- 提供版本号、更新提示、更新前兼容检查；签名发布和自动更新根据分发阶段安排。
- 明确“数据留本机，配置的模型服务仍会接收请求图片”，不要把本地存储宣传成全部本地推理。
- 保持现有 loopback/Origin/Host 防护。密钥可以逐步迁移至系统安全存储，备份提供“包含/不包含模型密钥”的明确选择。

## 四、功能提升：围绕可交付结果组织能力

### 第一优先级：批量生产闭环

现有变量矩阵和增量版本已提供很好的基础。下一步建议：

1. 保存批次为配方：参考图、模板、变量列、风格、模型与参数一起保存。
2. 支持 CSV/表格粘贴、列映射、缺失值提示、生成前预览每一条最终提示词。
3. 只重试失败项/指定项，保留原顺序与成功图，不让用户重复支付整批费用。
4. 暂停采用“当前项结束后暂停”；明确区分暂停与取消，恢复时不重跑已成功项。
5. 增加命名规则，例如 SKU、语言、渠道、序号；ZIP 带任务清单与提示词映射。
6. 支持按交付规格处理尺寸、格式、文件体积，并显示最终实际像素。AI 生成分辨率与本地导出尺寸分开表达。

成功指标：从准备素材到获得合格批次的总耗时、人工返工次数、失败恢复成本；不能只看生成了多少张。

### 第二优先级：中文改字和多语言改版

当前将用户希望的文字快照直接继承到生成结果，能省去识别费用，但它不证明模型真的画对了文字。建议区分“期望文字”与“已验证文字”。

- 提供“重新识别”和可选的生成后 OCR 校验，标记漏字、错字、删除未生效的区域。
- 根据任务需要，仅复查变更区域；供应商/本地 OCR 策略可配置，避免每次增加一整轮昂贵视觉调用。
- 新增确定性文字层：背景修复后，本地排版叠加文字，支持字体、字号、换行和对齐；保留 AI 自然融合方案给复杂透视或装饰文字。
- 将“换价格/换日期/换语言”做成模板任务，允许从表格批量生成，完成后展示差异和校验结果。

这条路线的竞争力在于正确率、可修正性和效率，而非只展示一次惊艳的改字效果。

### 第三优先级：品牌与商品素材一致性

将当前单一 stylePrompt 升级为项目资产规范：Logo、产品参考图、品牌色、字体、禁改区域和允许变动的内容。

第一版无需训练模型：先实现多参考图角色区分、结构化品牌提示词、确定性 Logo/文字叠加、区域保护、模板复用。UI 要区分硬约束与模型尽力遵守的偏好，不能仅靠提示词声称严格一致。

### 第四优先级：编辑结果可控

当前增强和扩图主要由改图提示词实现；提取素材也经生成模型再绘制。它们不等同于确定性放大、像素保真的扩展或原始像素抠图。

- 局部编辑：把已有参考图模式的框外保护扩展为可选通用能力，增加画笔/擦除蒙版。
- 抠图：提供实际透明通道的主体分割路径；“重新生成独立素材”作为另一种明确操作。
- 扩图：先展示实际新增画布、原图位置与尺寸，必要时把原图像素覆盖回结果，处理边缘融合。
- 变清晰：区分确定性超分/降噪与生成式细节增强，显示可能重构细节的模式。
- 对比：显示正确输入图，增加 100% 检视、局部放大和差异高亮；不要把缩小预览当作交付验收。

### 第五优先级：任务与成本透明

- 全局任务中心列出所有项目任务，统一排队、取消、重试和错误分类。
- 按模型配置限速和并发上限。目前一次生成内部并发限制为 2，不代表多个项目共享同一供应商额度时总并发也是 2。
- 展示视觉规划次数、图像请求次数、限流重试与补发。允许用户维护单价用于估算；供应商未提供 usage/价格时明确“估算/未知”。
- 多候选生成提供“普通候选/分别生成/自动判断”的明确策略或简洁高级选项，避免普通多候选强制依赖另一套视觉模型。
- 错误区分网络、额度、参数、内容拒绝、图片下载和本地磁盘故障；对不可重试错误停止，避免盲目补发。

## 五、竞争位置与价值主张

以下为官方公开资料对照与基于本项目代码的产品判断，不代表市场份额或用户需求调查。

| 产品 | 官方资料可确认的能力 | Layerive 应争取的空间 |
| --- | --- | --- |
| Adobe Firefly / Photoshop | Firefly 已整合生成、编辑、放大、背景处理与 Bulk 工作流；Photoshop 有 Generative Fill 和扩图。 | 在已有图片的中文改版、批量变量操作、可追溯版本和自配模型的效率上做得更集中。单独增加“扩图”难构成差异。 |
| Canva | Bulk Create 支持批量创建设计；Magic Studio 与品牌工具衔接。 | 加强导入已有图片后的精细改字、局部修改、失败恢复和生产记录，验证这部分需求。不能把变量表格本身当独家能力。 |
| ComfyUI | 本地开源节点式生成工作流，覆盖复杂多步骤组合。 | 为无需维护节点图的用户提供清楚的任务表单、预设和可靠交付。后续可接入成熟工作流，避免重造完整节点编辑器。 |

资料：[Firefly 工作区](https://helpx.adobe.com/firefly/web/get-started/access-the-app/firefly-workspace-overview.html)、[Photoshop Generative Fill](https://www.adobe.com/products/photoshop/generative-fill.html?ref_type=adv)、[Canva Bulk Create](https://www.canva.com/help/bulk-create/)、[Canva Magic Studio](https://www.canva.com/newsroom/news/magic-studio/)、[Comfy 官方介绍](https://support.comfy.org/articles/9806306061-about-comfy)。检索日期：2026-09-27。

建议首先验证的定位：**面向中文电商运营与小型设计团队，把已有商品图、海报批量改成可交付素材的本地工作台。**

价值主张可以落在具体动作：导入现有图 → 锁定品牌元素 → 从表格替换商品/价格/语言 → 检查差异 → 重试失败项 → 按渠道导出。

优先访谈两类用户：每周重复做大量商品图的运营；为多客户反复改海报的自由设计师。以各自实际任务观察，而非只问“想要什么功能”。游戏资产/角色一致性有潜力，但可能要求多参考、专用控制和更复杂流程，宜在前一场景验证后再扩展。

暂缓项：自建训练平台、通用无限画布、视频全家桶、自建模型聚合计费平台、完整多人实时编辑。它们都可能有价值，但会明显扩散当前修复与交付资源。

## 六、实施路线与验收

以下以一名熟悉项目的全栈开发者、现有模型接口可用为假设，是粗略排期，不是交付承诺；复杂图像算法与桌面分发可能增加时间。

| 阶段 | 时间参考 | 主要工作 | 退出条件 |
| --- | --- | --- | --- |
| A：可靠性 | 第 1–2 周 | B01–B07；批量草稿；桌面恢复存储；备份限额对齐与明确提示 | 7 项反例成为正式回归；重复提交不多建任务；输入和草稿不因常见操作丢失；支持范围内备份可恢复 |
| B：批量交付 | 第 3–4 周 | 统一规划任务/取消、失败项重试、模板保存、CSV/表格输入、命名与规格导出 | 用真实 30–50 项任务完成导入、生成、恢复、交付；不用手工重建失败批次 |
| C：差异化试点 | 第 5–8 周 | 品牌规范、改字结果校验、透明抠图或确定性文字层择一深入 | 5–10 名目标用户完成自己的重复任务；记录人工返工、完成时间、再次使用原因 |
| D：依据结果扩展 | 试点后 | 性能优化、模型/工作流适配、分发与更新、团队交付能力 | 以真实瓶颈排序；没有使用证据的功能不默认进入开发 |

核心指标建议：

- 首次成功导出用时，以及配置模型到第一次可用结果的转化。
- 每个任务最终被用户接受/导出的图片比例；生成成功率与业务验收率分开。
- 每张合格素材的人工操作数、模型调用次数、估算费用和时间。
- 批量失败后的恢复成功率，是否重复生成已成功项。
- 草稿丢失、版本来源错误、重复付费任务数量，目标为零。
- 目标用户一周内再次完成同类任务的比例，以及愿意付费的具体能力。

统计默认留在本地；若将来做远程分析，应由用户选择，不应偷偷上传提示词或图片。

商业验证可以围绕批量生产、品牌模板、交付工具和更新支持设计方案；先验证节约了多少真实工作，再测试价格。当前没有使用数据和付费访谈，不应直接声称某种订阅价格或用户规模成立。

## 下一轮开发的建议范围

最值得先交付的一轮是：保存 revision + PATCH 字段更新 + 提交幂等 + 版本引用修复 + 图片输出校验，并把本文反例纳入测试。这一轮提升的是信任基础。随后用“表格驱动的中文营销素材改版”做一个完整、可演示、可验收的产品流程。

实际改动功能、API、数据结构或重要约束时，应按项目维护契约同步更新 AGENTS.md 与相关用户说明；本次仅增加分析报告与隔离验证材料。
